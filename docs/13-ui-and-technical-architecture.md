# 13｜2D UI、資料驅動與技術架構草案

> **【提案／待決】** 使用者指定偏《遠行星號》的 2D 平面遊戲，認為多數星系可用模板＋AI 生成的幾張圖片呈現。引擎、平台、渲染 API、最終畫面樣式尚未正式定案。此處為可移交 Codex 的設計方向，**不是已存在程式碼**。

## 玩家看到的主要畫面

| 畫面 | 最低功能 | 避免的問題 |
|---|---|---|
| 銀河舊軍圖 | 星系座標、歷史航線、舊軍港、母星、情報最後更新時間 | 不把舊資料直接改成沒有歷史的全黑迷霧 |
| 星系航行畫面 | 2D 恆星、行星、空間站、商隊、敵艦、掃描點 | 不需要建造每顆行星的 3D 世界 |
| 艦隊編制 | 旗艦、戰鬥群、護衛／運輸／工程群、修理與載員容量 | 不把百艘船變成 100 個逐艦點擊頁 |
| 航行與補給 | 燃料、原料、航線、採集時間、停靠交易／搶劫／修船 | 不變成倉儲 ERP |
| 2D 戰鬥 | 兵力、戰線、旗艦危險、集火／護衛／撤退指令（待決） | 不以自動戰鬥當作沒有玩家決策的動畫 |
| 情報紀錄 | 舊圖 vs 最近偵察、控制權、駐軍、通行、已知遺產 | 不讓玩家猜不出為什麼被攔截 |
| 事件通訊 | 少量對話、圖示、可交互地點、航行日誌 | 不把 64 個事件寫成強迫道德選單 |
| 返鄉結算 | 同鄉人數、歸航艦數、戰損、路線、重要戰果 | 不加未經同意的強制最終戰 |

## 視覺資產「省工」的正確方式

**【方向】** 2D 星雲背景、行星貼圖、空間站、艦船俯視輪廓可用少量母素材組合；程序套用縮放、角度、顏色、燈光、粒子、視差、殘骸等變化。

**【提案】** 首個原型只用少量背景、恆星、行星、站點與可辨識艦船外形；不要先畫 300 張獨立星系 CG。美術省下來的時間留給 AI 指揮、航行、經濟、可視化和存檔測試。

**限制：** 美術重用不能讓重要地標在 UI 中完全沒有識別度；命名地標可有特殊背景／地形或建築插圖。遠古神器只需少量高辨識的畫面，不必每顆星系都有。

## 推薦系統模組切分

1. **UniverseSeed / Generator**：輸入世界種子，生成固定地標骨架與普通星系，保存戰前資料與當前可變資料。
2. **WorldClock / Simulation**：遊戲時間、局部勢力行動、接管前線、事件狀態更新。
3. **Map / Navigation**：星系座標與航線、過期情報視圖、移動可達性與路線成本。
4. **Fleet / Population**：旗艦、艦隊編制、可運載人口、作戰／工業分艦隊。
5. **Economy / Logistics**：原料、燃料、交易、採礦、恆星採集、回收、修造。
6. **Combat / AI**：艦船與編隊、目標選擇、戰場 AI、旗艦保護與撤退。
7. **Factions / VictorPriority**：地方勢力、友敵關係、戰略威脅、接管與駐軍。
8. **Events / Content**：資料驅動的事件條件、觸發、結果、唯一事件旗標。
9. **SaveGame / Repro**：生成種子＋玩家操作＋變更世界狀態＋時間戳；支持可重現 QA。

模組切分是工程提案，並非要求第一版建立九套完整服務架構；同一小型程式內也可先簡化實現。

## 狀態結構建議

| 物件 | 最少持久化欄位 |
|---|---|
| World | seed、world_time、chapter_or_session_flags、homeworld_id |
| StarSystem | id、座標、戰前用途、戰前所屬、當前勢力、星門狀態、資源、事件狀態 |
| IntelRecord | system_id、source、observed_at、observed_facts、quality |
| Fleet | fleet_id、所在星系、指令、ships、population、cargo、fuel |
| Ship | ship_id、class、hull_state、modules、crew、capacity、owner、flagship |
| Faction | faction_id、control、military_assets、relationship、current_goals |
| VictorTheater | known_targets、priorities、allocated_forces、occupied_systems |
| EventLog | 事件 id、triggered_at、結果、是否可再次觸發 |

### 關鍵不變條件

- 已探過的星系不會重進就重新抽一個現況；除非世界模擬真的使它變了。
- 舊軍圖的戰前記錄仍可查，現況情報可標示過期。
- 旗艦身分唯一且持續追蹤，沉沒按規則判定失敗。
- 人數不可超過艦隊能承載的設定上限而沒有清楚原因。
- 造船花費與獲得艦船不能重複結算。
- 戰勝國看見玩家與實際派兵追擊是兩個不同狀態。
- 存檔與讀檔不應造成無限刷獨特遠古遺物。

## 世界模擬效能策略【提案】

- **完整模擬**：玩家目前星系及正在交戰／近距離活動的艦隊。
- **簡化更新**：已知地方勢力、重大地標與戰勝國接管任務，以時間刻度更新政治／經濟結果。
- **休眠摘要**：普通無人星系只儲存資源、當前主人、最近事件與變動時間，不維持所有艦船每秒 AI。
- **戰場限制**：根據測試決定部署上限，不預先承諾 100 艘同場高精度模擬。
- **資產重用**：圖層、sprite atlas、簡單 shader／特效，不把背景裝飾當獨立昂貴 AI。

## 最先測試的 UI／技術缺口

- 玩家能在 30 秒內找到母星、旗艦、燃料、最鄰近三個可去星系嗎？
- 100 艘艦艇的編組能用有限操作完成，而不是開 100 個選單嗎？
- 舊圖標註與現況是否明顯區分，避免玩家把過期價格當成現價？
- 旗艦生命危險、撤退通道、補給即將用盡是否有清楚預警？
- 同一存檔讀取後，戰勝國接管、軍閥資產與已完成事件是否完全保持一致？

## 尚未選型

HTML5／WebGL／Canvas、其他 2D 引擎、PC／行動平台、視窗解析度、最低硬體、遊戲語言、自動化測試框架、多人與模組支援均沒有使用者定案。**不要因為聊天曾提過 HTML5 就假稱引擎已選。**

## 武器資料與介面的補充【提案】

武器藍圖需另存版本、有限觸發圖、每段投送類別與資源預算；艦隊 Doctrine 指向既有版本，不因編輯模板就免費改裝全軍。詳見 [W07](warfare-modular-blueprints.md)。裝配介面先解釋行為與最壞事件數，再考慮複雜視覺編輯器。

文件檢查工具只驗證本倉庫的 Markdown 路徑、錨點、標題和唯一 ID；不能證明遊戲可玩、引擎已選或數值正確。
